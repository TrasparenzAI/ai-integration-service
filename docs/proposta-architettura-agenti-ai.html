1. Contesto e architettura attuale

Il progetto AI Integration Service è un microservizio Spring Boot che espone API REST/SSE per l'interazione con modelli linguistici locali (Ollama) nel contesto di TransparenzAI. Attualmente il servizio:

  • Utilizza Spring AI 2.0.0-M4 come layer di astrazione sui modelli LLM
  • Si appoggia a Ollama per l'esecuzione locale di modelli open weight
  • Supporta tool MCP (Model Context Protocol) per l'accesso ai servizi TransparenzAI
  • Gestisce input multimodali: testo, immagini e audio (trascrizione via Whisper)
  • Offre output opzionale via Text-to-Speech (Kokoro)
  • Protegge le API con OAuth2/JWT (Keycloak)

Pattern agent-like già presenti

L'architettura attuale implementa già alcuni pattern tipici degli agenti AI, pur non essendo esplicitamente strutturata come tale:

Pattern attualeCorrispondenza nel mondo agent
CapturingToolCallback + tool loopAgentic loop: l'LLM decide quando invocare tool
ToolResultStore con correlationIdState management per sessione
Opzione think=true su qwen3Extended thinking / chain-of-thought planning
Pre-processing audio (Whisper → testo)Pipeline multi-step prima dell'LLM principale
History messaggi multi-turnMemoria conversazionale
Osservazione chiave Il servizio è sostanzialmente un agente implicito singolo: un unico modello (qwen3-next:80b) gestisce tutti i domini applicativi — bandi, normativa, dati, multimedia — con un sistema prompt generico. La proposta è di rendere questa struttura esplicita, modulare e ottimizzata.

2. Motivazioni per l'introduzione degli Agenti

Limiti dell'approccio attuale

  • Un solo modello per tutto: qwen3-next:80b è usato anche per task che richiederebbero modelli più leggeri (es. classificazione del dominio, gestione di tool call semplici), con latenza e costo computazionale eccessivi
  • Sistema prompt monolitico: un unico prompt in italiano cerca di coprire tutti i casi d'uso, diventando difficile da manutenere e ottimizzare
  • Logica concentrata nel controller: ChatStreamController gestisce routing, pre-processing, tool invocation e output, violando il principio di singola responsabilità
  • Scarsa estendibilità: aggiungere un nuovo dominio applicativo richiede modifiche al controller e al sistema prompt

Vantaggi attesi con gli Agenti

VantaggioImpatto pratico
Modello giusto per ogni taskRiduzione latenza e carico GPU per task di routing e tool calling
Prompt ottimizzati per dominioQualità delle risposte superiore su bandi, normativa, dati
Separazione responsabilitàCodice più manutenibile e testabile
Aggiunta di nuovi dominiBasta aggiungere un nuovo @Agent senza toccare l'esistente
OsservabilitàOgni agente è un'unità monitorabile indipendentemente
Contesto condiviso esplicitoIl "world" rende tracciabile cosa viene passato tra agenti

Principi di design

  1. Trasparenza verso i client: l'endpoint /v1/chat/stream rimane invariato; l'orchestrazione è interna al servizio
  2. Solo modelli open weight: tutti gli agenti usano modelli eseguibili localmente via Ollama, senza dipendenza da API cloud
  3. Contesto condiviso esplicito: il TransparenzaWorld formalizza cosa viene passato tra agenti
  4. Estendibilità per dominio: un nuovo dominio richiede solo un nuovo @Agent Spring bean
  5. Spring-first: Embabel si integra nativamente con Spring Boot, quindi tutti i bean esistenti (ChatClient, Feign, WebClient) restano riutilizzabili

ollama:qwen3-next:80b

MultimedialeAgent
ollama:minicpm-v + Whisper
Gestisce l'elaborazione di contenuti non testuali: trascrizione audio via Whisper STT, analisi e descrizione di immagini con un modello vision. Produce output testuale per gli altri agenti.

ollama:qwen2.5:14b
Interfaccia con i tool MCP di TransparenzAI per la ricerca e aggregazione di dati strutturati (appalti, enti, importi). Usa un modello leggero perché il task è prevalentemente di tool calling.

5. Integrazione con Embabel

Perché Embabel

Embabel è un framework open source (Apache 2.0) per la costruzione di agenti AI, progettato specificamente per l'ecosistema Spring. Si basa su Spring AI e introduce un livello dichiarativo per la definizione di agenti, azioni e obiettivi.

CaratteristicaValore per questo progetto
Spring-native (@Agent, @Action)Curva di apprendimento minima, skill Spring già presenti
Modello per agente configurabileMapping modello ↔ agente dichiarativo nell'annotazione
World object (contesto condiviso)Sostituisce l'attuale ToolResultStore in modo strutturato
Planning basato su precondizioni/postcondizioniL'orchestratore può ragionare sull'ordine di esecuzione
Integrazione Spring AI nativaChatClient, ToolCallback, MCP esistenti riutilizzabili

public class TransparenzaWorld {

    // Input dalla richiesta HTTP
    private String userQuery;
    private List<Message> conversationHistory;
    private List<Media>  attachedImages;

    // Prodotto dall'OrchestratorAgent

    private List<String> agentPlan;  // ordine di esecuzione pianificato

    // Prodotto dal MultimedialeAgent

    private String imageAnalysis;

    // Prodotto dal DatiTrasparenzaAgent
    private List<ToolResult> mcpResults;

    // Prodotto dall'agente di dominio principale
    private String domainAnalysis;

    // Prodotto dall'OrchestratorAgent al termine
    private String finalResponse;

    // Metadati
    private String correlationId;
    private Instant startTime;
}

@Agent(
    description = "Orchestratore centrale: classifica il dominio e coordina gli agenti specializzati",
    model = "ollama:qwen2.5:14b"  // modello leggero per decisioni di routing
)
public class OrchestratorAgent {

    @Action(
        description = "Classifica il dominio della richiesta utente",
        post = { "world.detectedDomain != null" }
    )
    public TransparenzaWorld classificaDominio(TransparenzaWorld world) {
        // prompt conciso: solo classificazione, nessun ragionamento lungo
        String domain = chatClient.prompt()
            .system("Classifica la richiesta in uno di: bandi, normativa, multimedia, dati. " +
                    "Rispondi con una sola parola.")
            .user(world.getUserQuery())
            .call().content();
        world.setDetectedDomain(domain.trim().toLowerCase());
        return world;

Esempio: BandiAppaltiAgent

@Agent(
    description = "Analisi di bandi di gara, contratti e documentazione appalti ANAC",
    model = "ollama:qwen3-next:80b-a3b-instruct-q4_K_M"
)
public class BandiAppaltiAgent {

    private final SyncMcpToolCallbackProvider mcpTools;

    @Action(
        description = "Analizza la documentazione relativa a un appalto",
        pre  = { "world.detectedDomain == 'bandi'" },
        post = { "world.domainAnalysis != null" }
    )
    public TransparenzaWorld analizzaAppalto(TransparenzaWorld world) {
        String analysis = chatClient.prompt()
            .system(SYSTEM_PROMPT_BANDI)  // prompt ottimizzato per appalti
            .user(world.getUserQuery())
            .tools(mcpTools.getToolCallbacks())
            .call().content();
        world.setDomainAnalysis(analysis);
        return world;
    }

    private static final String SYSTEM_PROMPT_BANDI =
        "Sei un esperto di appalti pubblici e del Codice dei Contratti (D.Lgs 36/2023). " +
        "Analizza la documentazione fornita e rispondi con precisione giuridica. " +
        "Cita sempre il riferimento normativo pertinente.";
}

Integrazione nel controller (lato client invariato)

@PostMapping("/stream")
public SseEmitter streamChat(@RequestBody ChatRequest request,
                              @AuthenticationPrincipal Jwt jwt) {
    SseEmitter emitter = new SseEmitter(sseEmitterProperties.getTimeout());

    TransparenzaWorld world = TransparenzaWorld.builder()
        .userQuery(request.getQuery())
        .conversationHistory(request.getHistory())
        .correlationId(UUID.randomUUID().toString())
        .build();

    // L'AgentPlatform di Embabel gestisce il ciclo di pianificazione
    // e invocazione degli agenti in modo asincrono
    agentPlatform.runAgentAsync(OrchestratorAgent.class, world)
        .subscribe(
            event  -> emitter.send(toSseEvent(event)),
            error  -> emitter.completeWithError(error),
            ()     -> emitter.complete()
        );

    return emitter;
}

6. Strategia dei modelli Open Weight

Tutti i modelli devono essere eseguibili localmente via Ollama, senza dipendenza da API cloud. La selezione privilegia la disponibilità nel registry Ollama e la compatibilità con Ollama's tool-calling API.

AgenteModello propostoParametriMotivazione
OrchestratorAgent
DatiTrasparenzaAgent		 qwen2.5:14b 14B Rapido, ottimo tool calling, basso consumo GPU per task di routing
BandiAppaltiAgent
NormativaAgent		 qwen3-next:80b (attuale) 80B (MoE) Massima qualità per ragionamento complesso su testi normativi
MultimedialeAgent (immagini) minicpm-v:8b 8B Modello vision leggero, buon bilanciamento qualità/velocità
MultimedialeAgent (audio) Whisper (attuale) — Già integrato, eccellente per italiano, nessun cambio necessario
Risparmio computazionale atteso Oggi il 100% delle richieste usa qwen3-next:80b. Con la multi-agent architecture, le richieste di routing (OrchestratorAgent) e tool calling semplice (DatiTrasparenzaAgent) userebbero qwen2.5:14b, liberando capacità GPU per i task che ne hanno davvero bisogno.

7. Piano di migrazione

La migrazione è progettata per essere incrementale e non distruttiva: ogni fase è deployabile indipendentemente senza impatto sui client.

1
Infrastruttura base — nessun impatto funzionale
Aggiunta dipendenza Embabel al pom.xml. Creazione di TransparenzaWorld e AgentConfig. Il controller e il comportamento rimangono identici. Obiettivo: validare la compatibilità di Embabel con Spring Boot 4.x e Spring AI 2.x.
2
MultimedialeAgent — caso più isolato
La logica di pre-processing audio (Whisper) e analisi immagini è già separata nel controller. È il candidato ideale per la prima migrazione: basso rischio, chiara separazione di responsabilità, possibilità di testare il pattern Embabel in produzione.
3
DatiTrasparenzaAgent — isolamento tool MCP
Estrazione della logica di invocazione tool MCP in un agente dedicato. Semplifica significativamente il ChatStreamController e rende esplicita la separazione tra "recupero dati" e "ragionamento". Il ToolResultStore esistente può essere sostituito dal World di Embabel.
4
Agenti di dominio + OrchestratorAgent
Introduzione di BandiAppaltiAgent e NormativaAgent con prompt specializzati. Infine l'OrchestratorAgent come punto di ingresso unico che sostituisce la logica di routing nel controller. L'endpoint REST rimane invariato.

8. Rischi e mitigazioni

RischioProbabilitàImpattoMitigazione
API Embabel instabile (v0.x) Media Alto Incapsulare Embabel in un layer interno; esporre solo interfacce proprie. Monitorare le release note prima di ogni aggiornamento.
Latenza orchestratore → sotto-agenti Media Medio Usare modello leggero (qwen2.5:14b) per il routing. Limitare il prompt di classificazione a poche centinaia di token.
Streaming SSE con agenti asincroni Media Alto Verificare il supporto Flux/reactive di Embabel nella versione target. Se necessario, implementare un adattatore SSE custom.
Context window del World troppo grande Bassa Medio Passare nel World solo i dati necessari per ogni agente; evitare di serializzare interi documenti nel contesto condiviso.
Compatibilità Spring Boot 4.x + Embabel Bassa Alto Verificare nella Fase 1 (infrastruttura) prima di procedere. Embabel è progettato per Spring AI 2.x che è la versione usata dal progetto.
Disponibilità GPU per più modelli in parallelo Media Alto Configurare Ollama con keep_alive opportuno; valutare esecuzione sequenziale degli agenti in prima fase.

9. Conclusioni e prossimi passi

Sintesi della proposta

L'introduzione di un'architettura multi-agent basata su Embabel è vantaggiosa e coerente con la direzione del progetto per le seguenti ragioni:

  • Il dominio applicativo (trasparenza ANAC, appalti, normativa) è naturalmente multi-dominio e beneficia di agenti specializzati con prompt ottimizzati
  • L'uso di modelli diversi per agenti diversi permette di ottimizzare latenza e consumo GPU senza compromettere la qualità dei task complessi
  • Embabel è Spring-native e non richiede un cambio di paradigma radicale rispetto all'architettura esistente
  • La migrazione incrementale per fasi garantisce la continuità del servizio e permette di validare ogni fase in isolamento
  • Il design trasparente verso i client significa che nessun consumer del servizio deve essere aggiornato
Attenzione Embabel è in versione 0.x (early development). Prima di adottarlo in produzione è fondamentale verificare la stabilità dell'API nella Fase 1 e valutare la community e la roadmap del progetto. In alternativa, è possibile implementare un orchestratore custom leggero su Spring AI senza Embabel, sacrificando il planning dichiarativo ma guadagnando in stabilità.

Prossimi passi consigliati

  1. Proof of Concept (Fase 1): aggiungere Embabel al progetto e verificare la compatibilità con Spring Boot 4.x e Spring AI 2.0.0-M4 in un branch dedicato
  2. Spike MultimedialeAgent (Fase 2): implementare e testare il primo agente in isolamento, misurando latenza e qualità rispetto all'approccio attuale
  3. Decisione go/no-go su Embabel: dopo il PoC, valutare se proseguire con Embabel o implementare un orchestratore custom
  4. Identificazione dei domini: raffinare la tassonomia degli agenti con gli stakeholder di dominio (esperti ANAC, utenti finali)
  5. Benchmark modelli: confrontare qwen2.5:14b vs qwen3-next:80b su task di routing per validare l'assunzione di risparmio computazionale
